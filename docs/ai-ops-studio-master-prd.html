02

사용자와 권한

마켓플레이스 계정 유형과, 판매자로 활성화된 조직 내부 역할을 분리한다.

GUEST

비회원

로그인 없이 상품을 둘러보고 주문번호로 배송·취소 상태를 확인한다.

CONSUMER

소비자

회원가입한 구매자. 마켓플레이스의 모든 판매자 상품을 구매·문의한다. 프로필에서 판매자로 전환할 수 있다.

SELLER

판매자

본인 상품(옷·신발 등)을 등록해 판매한다. 판매마다 플랫폼 수수료가 차감되며, 콘솔에서 문의·주문·매출을 관리한다.

ADMIN

총관리자

플랫폼 전체를 운영한다. 판매자 승인·정지, 수수료·플랜 정책, 마켓플레이스 전체 매출과 신고 처리를 담당한다.

가입·활성화 경로

경로 A · 소비자로 가입 후 전환

일반 회원가입 → 쇼핑 이용 → 마이페이지에서 “비즈니스로 가입하기” 활성화 → 판매자 온보딩(상점명·카테고리·정산 계좌·수수료 동의) → 무료 입점 플랜으로 시작한다.

경로 B · 판매자로 바로 가입

회원가입 화면에서 “판매자로 시작하기”를 선택하면 동일한 판매자 온보딩으로 바로 이동한다. 가입 완료 시점부터 소비자 기능도 같은 계정으로 함께 사용한다.

계정 통합 원칙

소비자와 판매자는 별도 계정이 아니라 한 계정이 가질 수 있는 상태다. 판매자 활성화는 언제든 가능하지만, 판매자 비활성화는 정산 미완료 건이 없어야 처리된다.

판매자 조직 내부 역할

판매자로 활성화되면 그 계정을 중심으로 상점(조직)이 하나 생성된다. 상점에 직원을 초대하면 아래 세부 역할로 나눠 관리한다.

문의 상태 머신

AI 파이프라인 실제 동작 · 구현 코드 기준

면접·코드 리뷰에서 “AI가 정확히 어디서 어떻게 호출되나요”에 바로 답하기 위한 절차 기록이다. 아래는 customer-support-answer(+ 그 안에서 함께 도는 support-triage) 경로를 기준으로 하며, 네 페르소나 전체를 버튼 클릭 단위로 정리한 표는 15. 기능별 구현 상세에 있다.

단계파일역할
진입점services/core-api/app/api/routes/ai.pyPOST /api/v1/ai/reply — 요청을 받아 서비스에 위임하고 문의를 저장한다.
오케스트레이션services/core-api/app/services/openrouter.pyOpenRouterSupportService.generate_reply() — Langfuse trace 시작, 프롬프트 컴파일, 안전 규칙, OpenRouter 호출을 순서대로 실행한다.
프롬프트 조회services/core-api/app/services/prompts.pyPromptRepository.compile() — Langfuse에서 prompt name+label로 버전을 가져와 변수 치환, 실패 시 로컬 fallback 문자열 사용.
PII 마스킹services/core-api/app/services/tracing.pymask_otel_spans — Langfuse로 나가는 모든 span 속성에서 이메일·휴대전화·카드번호 패턴을 치환.
호출자apps/demo-store/src/api.ts의 askSupport고객 쇼핑몰의 AI 상담 위젯이 유일한 실제 호출처. Ops Console은 결과를 조회만 한다.

요청 한 번의 실제 처리 순서

  1. Langfuse 루트 span 생성 — answer-customer-inquiry. request_id가 있으면 그 값을 시드로 trace_id를 결정해, 같은 요청을 재시도해도 같은 trace로 묶인다.
  2. 프롬프트 조회 (Retriever span) — retrieve-support-prompt. Langfuse에서 customer-support-answer prompt의 production label 버전을 가져온다. 이름은 “Retriever”이지만 실제로는 지식 문서 검색이 아니라 프롬프트 버전 조회다 — 진짜 RAG는 아직 없다(아래 한계 참고).
  3. 변수 치환 — 프롬프트 템플릿의 {{question}}, {{order_context}}, {{policy_context}}를 요청 값으로 채운다. order_context와 policy_context는 브라우저가 보낸 값을 그대로 신뢰한다 — 서버가 Commerce API를 다시 조회해 검증하지 않는다.
  4. 모델·파라미터 결정 — 조회된 prompt의 config JSON(model, temperature, max_tokens, provider.*)을 사용한다. Langfuse를 못 쓰거나 config가 비어 있으면 .env의 OPENROUTER_DEFAULT_MODEL과 코드 내 FALLBACK_CONFIG로 대체한다.
  5. 키워드 안전 규칙 — HUMAN_HANDOFF_KEYWORDS = ("분쟁", "소송", "신고", "고액 환불", "개인정보 유출"). 질문 원문에 이 문자열이 포함되면 LLM 응답과 무관하게 requires_human = true로 확정한다. 모델이 추정한 신뢰도 점수가 아니라 단순 문자열 매칭이다.
  6. API Key 없음 fail-safe — OPENROUTER_API_KEY가 비어 있으면 실제 LLM 호출 자체를 생략하고 “상담원에게 이관합니다” 고정 문구 + requires_human=true를 즉시 반환한다.
  7. OpenRouter 호출 (Generation span) — generate-support-reply. langfuse.openai.OpenAI(일반 openai.OpenAI가 아니라 Langfuse가 계측을 감싼 래퍼)로 chat.completions.create()를 호출한다. 이 한 줄 호출만으로 입력·출력·토큰 사용량·비용이 자동으로 Langfuse에 기록된다.
  8. 응답 처리 — completion.choices[0].message.content를 답변으로, completion.model을 “실제로 사용된 모델”로 기록한다. provider.allow_fallbacks=true면 OpenRouter가 요청한 모델이 아닌 다른 provider로 자동 대체할 수 있어 completion.model이 요청한 model과 다를 수 있다.
  9. 저장 — Langfuse trace와는 별도로, inquiry_store.save_exchange()가 core-api 자체 SQLite(support.db)에 문의·대화·메시지를 저장한다. Langfuse가 다운돼도 이 저장은 영향받지 않는다.

  "provider": { "allow_fallbacks": true, "data_collection": "deny" }
}

model·temperature·max_tokens·provider.* 다섯 값은 전부 Langfuse prompt의 config에서 나온다. 애플리케이션 코드에는 이 값들이 하드코딩돼 있지 않다 — 그래서 모델을 바꾸는 데 재배포가 필요 없다.

왜 OpenRouter인가

  • 여러 provider를 API Key 하나·청구 하나로 통합
  • ~model-slug “latest alias”로 업스트림이 신모델을 내면 재배포 없이 자동 추적
  • provider.allow_fallbacks로 1차 provider 장애 시 자동 대체
  • provider.data_collection: deny로 학습에 데이터를 쓰지 않는 provider 경로만 강제
  • 이전에는 google-genai SDK로 Gemini를 직접 호출했으나, 이번 세션에 이 프로젝트를 OpenRouter로 전환했다(docs/langfuse-tracing.md 참고).

왜 Langfuse에서 prompt·config를 가져오는가

  • 모델 교체 = 새 prompt version + production label 이동, 앱 재배포 불필요(단, prompt cache TTL 기본 300초만큼 지연 가능)
  • 모든 trace에 사용된 prompt 버전·모델·토큰 사용량·지연시간이 자동 기록 → 답변을 나중에 재현 가능
  • Langfuse가 죽어도 FALLBACK_PROMPT/FALLBACK_CONFIG로 서비스는 계속되지만, 이 모드에서는 모델이 OPENROUTER_DEFAULT_MODEL로 고정된다(재배포 없는 전환 이점이 일시적으로 사라짐).
  • gateway 필드가 "openrouter"가 아니면 코드가 ValueError를 던진다 — prompt config가 실수로 다른 게이트웨이를 가리켜도 엉뚱한 비밀값을 쓰지 않도록 막는 장치다.

PII 마스킹

Langfuse client 생성 시 mask_otel_spans 콜백을 등록해둔다. 이메일(정규식), 한국 휴대전화 번호, 13~19자리 카드번호 패턴이 모든 OTel span 속성에서 자동 치환된 뒤 Langfuse로 전송된다 — 호출부마다 마스킹을 기억해서 적용하는 게 아니라 SDK 레벨에서 강제된다.

A · 인증 — 이메일/비밀번호 + Google 로그인

사용 기술

  • 비밀번호: bcrypt.hashpw 직접 호출(passlib 미사용). 72바이트 제한을 피하려 SHA-256으로 먼저 다이제스트한 뒤 bcrypt 처리.
  • 세션: PyJWT, HS256, 7일 만료. payload는 {sub: customer_id, iat, exp}뿐 — role은 토큰에 안 넣고 매 요청마다 DB에서 다시 계산.
  • Google: Google Identity Services(GIS) 브라우저 팝업 → id_token 획득 → 서버가 Google tokeninfo 엔드포인트로 검증(JWKS 클라이언트 없이 단순 HTTP GET 한 번).

트리거 조건

  • 회원가입/로그인 폼 제출 시 즉시.
  • Google 버튼 클릭 → 팝업에서 계정 선택 성공 시.
  • role은 저장된 값이 아니라 매 요청마다 파생: is_admin이면 ADMIN, organizations.owner_customer_id가 있으면 SELLER, 아니면 CONSUMER.

Google 로그인 처리 순서

  1. demo-store가 GIS 스크립트로 팝업을 띄우고 id_token(JWT)을 받는다.
  2. POST /auth/google { id_token } 전송.
  3. 서버가 GET https://oauth2.googleapis.com/tokeninfo?id_token=... 호출.
  4. aud(토큰 대상)가 서버의 GOOGLE_CLIENT_ID와 일치하는지, email_verified인지 검증 — 하나라도 틀리면 401.
  5. 이메일로 기존 customers row를 찾고, 없으면 무작위 비밀번호 해시(로그인 불가능한 값)로 새로 만든다 — 소셜 로그인 계정도 같은 customers 테이블 한 곳에 산다.
  6. create_access_token()으로 JWT 발급, 이메일/비밀번호 로그인과 동일한 응답 형태로 반환.

analytics.py의 모든 숫자는 SQL SUM/COUNT다. commerce-insight 페르소나는 이 숫자가 이미 계산된 뒤에만 호출된다 — LLM이 매출을 계산하는 경로는 코드 어디에도 없다.

  • 멱등성: external_event_id가 UNIQUE + INSERT OR IGNORE. 예: "{order_id}:PAYMENT_CONFIRMED" — 같은 결제 확인 요청이 재시도돼도 매출이 두 번 잡히지 않는다.
  • 집계 기준: 이벤트가 발생한(occurred_at) 달을 기준으로 계산한다. 주문 상태의 현재값이 아니라 이벤트 원장을 다시 읽어 계산하므로, 다음 달에 환불이 나도 이번 달 매출이 소급 수정되지 않는다.
  • ops-console 경로: "매출 분석" 페이지 → GET /api/v1/revenue/summary?period= (core-api) → CommerceClient가 GET http://localhost:8001/analytics/summary?period=를 프록시 호출 → mock-commerce-api가 SQL 집계 → 그대로 반환. core-api는 숫자를 다시 계산하지 않고 통과시킨다.

D · AI ① customer-support-answer + support-triage — 문의 위젯

두 페르소나는 한 요청 안에서 순서대로 실행된다. 자세한 단계별 근거·한계는 05. AI Ops PRD에 이미 정리돼 있으므로, 여기서는 "클릭 → 저장"까지의 압축본만 다룬다.

  1. 고객이 문의창에 질문 입력 후 전송 클릭 → demo-store askSupport()가 POST /api/v1/ai/reply 호출.
  2. core-api OpenRouterSupportService.generate_reply()가 Langfuse 루트 span(answer-customer-inquiry)을 연다.
  3. 먼저 _classify_inquiry()가 support-triage 프롬프트로 OpenRouter를 호출해 {category, risk, requires_human} JSON을 받는다(중첩 span classify-inquiry).
  4. 이어서 _compile_prompt()가 customer-support-answer 프롬프트를 Langfuse에서 가져와 변수 치환하고, _generate_with_openrouter()가 실제 답변을 생성한다(span generate-support-reply).
  5. requires_human은 triage 결과의 risk == HIGH이거나, 질문 원문에 HUMAN_HANDOFF_KEYWORDS(분쟁·소송·신고·고액 환불·개인정보 유출) 문자열이 있으면 무조건 true — 두 신호를 OR로 결합해 AI 판단 하나에만 이관을 맡기지 않는다.
  6. inquiry_store.save_exchange()가 core-api 자체 support.db에 문의·대화·메시지를 저장한다(Langfuse trace와는 별개 저장소).
  7. requires_human=true면 core-api가 즉시 DiscordNotifier.send()로 상담원 이관 알림을 보낸다(웹훅 미설정 시 조용히 스킵).

J · 판매자·관리자 콘솔 — 로그인, 문의 라우팅, AI 리포트 3종

ops-console은 원래 인증 없는 관리자 전용 화면이었다. 지금은 같은 화면이 로그인한 계정의 role에 따라 다르게 보이는 멀티테넌트 콘솔이다 — SELLER는 본인 상점만, ADMIN은 플랫폼 전체를 본다.

  1. 로그인: ops-console이 mock-commerce-api의 POST /auth/login을 직접 호출한다(core-api를 거치지 않음 — demo-store와 동일 패턴). 응답의 customer.role이 SELLER/ADMIN이 아니면 콘솔 접근을 거부한다.
  2. 권한 검증은 core-api가 mock-commerce-api에 되묻는 방식: core-api는 JWT를 직접 디코드하지 않는다. app/services/identity.py의 require_org_access()/require_admin()이 매 요청마다 CommerceClient.verify_identity(token)으로 GET /customers/me를 호출해 "이 토큰이 정말 이 조직 소유자인가/관리자인가"를 확인한다.
  3. 문의 → 판매자 자동 라우팅: 문의에 order_id가 있으면 POST /api/v1/ai/reply가 CommerceClient.get_order_org_id()로 그 주문의 실제 판매자를 조회해 inquiries.organization_id에 저장한다(클라이언트가 보낸 값은 신뢰하지 않는다). 조회 실패는 예외를 삼키고 None으로 폴백 — 조직 귀속은 부가 기능이라 원본 문의 저장을 막으면 안 된다.
  4. 세 AI 리포트의 데이터 경계: daily-seller-report는 seller_daily_snapshot(org_id, date)로 딱 그 판매자의 상품만; platform-daily-traffic은 platform_daily_traffic(date)로 org 필터 없이 전체 판매자를; seller-market-share-report는 seller_market_share(period)로 전체 활성 판매자를 비교한다. 뒤의 둘은 require_admin()으로 막혀 있고, 전용 Discord 채널(ADMIN_DISCORD_WEBHOOK_URL)로만 나간다 — 판매자용 채널(DISCORD_WEBHOOK_URL)과 물리적으로 분리.

"매출 점유율"의 실제 계산 — GMV가 아니라 플랫폼 자신의 수익

판매자 매출 자체(GMV)를 비교하면 오해가 생긴다. 이 사이트가 실제로 버는 돈은 판매 수수료 + 판매자 구독 플랜 요금뿐이다. organizations.plan 컬럼(FREE/BASIC/PRO/BUSINESS)과 고정 월 요금표를 더해 이렇게 계산한다:

platform_contribution = gross_revenue × organizations.commission_rate + PLAN_MONTHLY_FEES[plan]
# PLAN_MONTHLY_FEES = { FREE: 0, BASIC: 35,000, PRO: 150,000, BUSINESS: 300,000 }
share_pct = platform_contribution / total_platform_revenue × 100

그래서 무료 입점 판매자가 판매액은 훨씬 커도, 유료 플랜 판매자보다 플랫폼 매출 점유율은 낮게 나올 수 있다 — 실제 시드 데이터에서 "라인 클로젯"(BUSINESS, 판매액 3위)이 "무드 스토리"(FREE, 판매액 1위)보다 훨씬 높은 점유율을 갖는 것으로 확인했다. 구독·결제 시스템은 아직 없으므로 플랜 요금은 PLAN_MONTHLY_FEES 상수를 쓰는 가정치다.

K · 배포 — 왜 Next.js가 아니라 Vite인가

애초에 Next.js가 필요 없는 구조

  • demo-store·ops-console 둘 다 순수 클라이언트 SPA다 — 서버 사이드 렌더링, 파일 기반 라우팅, API Route 같은 Next.js 고유 기능을 하나도 쓰지 않는다.
  • "API 서버"는 이미 완전히 분리된 FastAPI 서비스(core-api, mock-commerce-api)로 존재한다. Next.js의 API Route는 "프런트 프로젝트 안에 백엔드를 욱여넣는" 기능인데, 이 프로젝트는 처음부터 백엔드가 따로 있어서 그 기능 자체가 무의미하다.
  • SEO가 중요한 공개 마케팅 페이지가 아니라 로그인 후 쓰는 대시보드·쇼핑 데모다 — SSR/SSG로 얻는 이점(초기 HTML에 콘텐츠 포함, 크롤러 대응)이 거의 없다.
  • Next.js로 옮기면 라우팅·데이터 페칭·빌드 파이프라인을 전부 다시 짜야 한다 — 지금 구조(React Query + 직접 fetch)를 그대로 못 쓴다. 없는 문제를 해결하려고 실제 마이그레이션 비용을 지불하는 셈이다.

Vite가 실제로 준 이점

  • 개발 서버 시작·HMR이 번들러 기반 도구보다 훨씬 빠르다 — 이 세션 내내 pnpm dev 한 번 띄워두고 수백 번 코드를 고치는 동안 체감됐다.
  • 빌드 결과물이 index.html + 정적 JS/CSS 몇 개뿐이다 — 배포 대상이 "그냥 정적 파일"이라 어떤 정적 호스팅에도 그대로 올라간다.
  • apps/demo-store, apps/ops-console 둘 다 vite.config.ts 하나로 끝난다. Next.js였다면 앱 라우터 구조, 미들웨어, 환경변수 접두사 규칙(NEXT_PUBLIC_*) 등 프레임워크 고유 규약을 새로 익히고 맞춰야 했을 것이다.

Vercel 배포 실제 방법

Vercel은 Next.js 전용 플랫폼이 아니라 프레임워크에 무관하게 정적 빌드 결과물을 배포할 수 있는 호스팅이다. Vite 프로젝트는 "Other"가 아니라 Vite 프리셋을 자동 인식한다.

  1. 이 저장소는 모노레포이자 서로 다른 두 SPA(demo-store, ops-console)를 담고 있으므로, Vercel 프로젝트를 2개 만든다(같은 GitHub 저장소를 두 번 import).
  2. 각 프로젝트의 Root Directory를 apps/demo-store, apps/ops-console로 각각 지정한다.
  3. Framework Preset은 자동으로 "Vite"가 잡힌다. 수동 설정 시: Build Command pnpm build(또는 vite build), Output Directory dist.
  4. 환경변수(VITE_CORE_API_URL, VITE_COMMERCE_API_URL, VITE_GOOGLE_CLIENT_ID)를 Vercel 프로젝트 설정의 Environment Variables에 등록한다 — 로컬 .env와 별개로, 배포된 백엔드의 실제 URL을 가리켜야 한다.
  5. pnpm 워크스페이스이므로 Vercel의 Install Command가 루트에서 pnpm install을 실행하도록 두고, Root Directory는 위 3번처럼 앱별로 분리한다 — 워크스페이스 의존성(@ai-ops/shared-types)은 pnpm이 자동으로 링크한다.
백엔드(core-api, mock-commerce-api)는 Vercel에 그대로 못 올린다

Vercel의 실행 모델은 요청마다 뜨고 죽는 서버리스 함수다. 이 프로젝트의 core-api는 DailySellerReportScheduler/PlatformTrafficScheduler/SellerMarketShareScheduler처럼 프로세스가 계속 살아있어야 도는 asyncio 백그라운드 루프를 lifespan에 등록해뒀다 — 서버리스 환경에서는 요청 사이에 프로세스가 꺼지므로 이 스케줄러들이 예정된 시각까지 깨어있을 거라는 보장이 없다. FastAPI 두 서비스는 상시 실행되는 컨테이너/VM 호스팅(Render, Railway, Fly.io 등)에 올리고, 프런트엔드(Vercel)의 VITE_CORE_API_URL/VITE_COMMERCE_API_URL이 그 주소를 가리키게 하는 구성이 맞다.

이 섹션에서 정직하게 밝히는 것

commerce-insight/commerce-monthly-report는 요청마다 새로 계산될 뿐 DB에 이력이 남지 않는다(지난달 리포트를 다시 보려면 그 기간으로 재생성해야 한다). support-triage 실패 시 키워드 폴백은 HUMAN_HANDOFF_KEYWORDS 5개 문자열 매칭이라 표현을 바꾸면 못 잡는다. Discord 실패는 재시도 없이 그냥 false를 반환한다. 전부 포트폴리오 MVP 범위에서 의도적으로 남긴 단순화다.

  • 처리 과정이 실시간 대시보드와 실행 로그에 반영된다.
  • 실패한 외부 작업을 확인하고 안전하게 재실행한다.
  • 판매·환불 이벤트로 전월 비교와 상품 순위를 계산한다.
  • 광고비·수수료 입력 시 추정 순이익을 재계산한다.
  • AI 월간 리포트와 Discord 요약이 같은 집계 수치를 사용한다.
  • Basic·Pro·Business 기능 접근이 서버에서 제한된다.

  • 3분 내외 핵심 시나리오 영상이 있다.
  • 아키텍처와 기술 결정 기록이 있다.
  • 성능 개선 전후 수치와 테스트 결과가 있다.

  • 월별 매출·환불·순이익 분석 데모를 1분 내 설명할 수 있다.
