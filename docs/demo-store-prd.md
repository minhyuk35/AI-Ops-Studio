## 1. 문서 목적

이 문서는 현재 데모 수준의 Everyday Market을 실제 주문 흐름을 재현할 수 있는 포트폴리오형 쇼핑몰로 확장하기 위한 제품 요구사항을 정의한다.

핵심 방향은 다음과 같다.

1. 고객이 상품을 발견하고 결제한 뒤 배송·취소·반품까지 스스로 처리할 수 있어야 한다.
2. 고객의 문의와 AI 답변은 단순 채팅으로 끝나지 않고 문의 티켓과 대화 이력으로 저장되어야 한다.
3. 주문, 결제, 배송, 문의 데이터는 AI Ops Studio 운영자 화면에서 추적할 수 있어야 한다.
4. 실제 배포 서비스에서 공통적으로 제공하는 필수 기능을 P0 범위에 우선 포함한다.
5. 포트폴리오 프로젝트이지만 금액·재고·주문 상태·권한 같은 핵심 규칙은 실제 서비스 수준으로 설계한다.

## 3. 제품 정의

### 3.1 한 문장 정의

Everyday Market은 패션과 리빙 상품을 탐색·구매하고, 주문 이후 배송과 교환·반품 및 AI 고객지원을 한곳에서 처리할 수 있는 반응형 쇼핑몰이다.

### 3.2 핵심 가치

- 고객: 원하는 상품을 빠르게 찾고 추가 비용과 배송일을 이해한 상태에서 안전하게 구매한다.
- 운영자: 주문과 문의가 연결되어 고객 상황을 반복 확인하지 않고 해결할 수 있다.
- 프로젝트 관점: 일반 쇼핑몰과 AI 운영 자동화가 하나의 데이터 흐름으로 연결되는 것을 보여준다.

### 3.3 제품 원칙

1. 가격, 재고, 배송비, 예상 도착일은 결제 직전에 갑자기 달라지지 않는다.
2. 사용할 수 없는 버튼은 숨기기보다 이유와 다음 행동을 설명한다.
3. 주문 상태는 고객 언어로 표시하고 내부 상태값을 그대로 노출하지 않는다.
4. AI는 확인된 상품·주문·정책 정보만 사용한다.
5. 취소·환불처럼 금전 상태를 바꾸는 행동은 AI가 임의 실행하지 않는다.
6. 모바일 화면을 우선 설계하고 데스크톱으로 확장한다.
7. 비회원도 상품 탐색과 구매가 가능해야 한다.

## 4. 목표와 성공 지표

### 4.1 제품 목표

- 홈에서 주문 완료까지 끊기지 않는 구매 여정을 제공한다.
- 주문 완료 후 배송조회와 취소·반품을 고객이 직접 처리한다.
- 고객 문의의 100%를 주문·사용자·대화 이력과 연결한다.
- AI가 답변한 문의와 상담원 이관 문의를 운영자 화면에서 구분한다.
- 결제 실패, 품절, 중복 요청 등 실제 운영에서 발생하는 예외를 처리한다.

### 4.2 핵심 지표

| 지표 | 정의 | 초기 목표 |
|---|---|---:|
| 구매 전환율 | 주문 완료 세션 / 상품 상세 방문 세션 | 데모 데이터 수집 후 기준선 설정 |
| 장바구니 이탈률 | 장바구니 진입 후 주문 미완료 세션 비율 | 추세 관찰 |
| 결제 성공률 | 승인 완료 / 결제 요청 | 95% 이상(테스트 결제 기준) |
| 검색 무결과율 | 결과가 0건인 검색 / 전체 검색 | 10% 이하 |
| AI 자동 해결률 | 상담원 이관 없이 종료된 문의 / 전체 문의 | 60% 이상 |
| 문의 문맥 연결률 | order_id 또는 product_id가 연결된 문의 비율 | 95% 이상 |
| 환불 처리 가시성 | 단계가 고객에게 표시된 환불 요청 비율 | 100% |

### 4.3 가드레일 지표

- 재고 초과 주문: 0건
- 결제 승인 금액 불일치: 0건
- 중복 결제·중복 주문: 0건
- 개인정보가 Langfuse에 마스킹 없이 저장된 건: 0건
- 상담원 승인 없이 AI가 금전 상태를 변경한 건: 0건

## 5. 사용자 정의

### 5.1 비회원 방문자

- 카테고리와 검색으로 상품을 찾는다.
- 상품 정보, 배송비, 반품 가능 조건을 확인한다.
- 회원가입 없이 장바구니와 주문서까지 이동한다.

### 5.2 회원 고객

- 찜, 최근 본 상품, 배송지, 주문 이력을 관리한다.
- 배송조회, 취소, 교환·반품, 재구매를 수행한다.
- 주문과 연결된 AI 상담을 이용하고 이전 문의를 확인한다.

### 5.3 구매 후 문제를 해결하려는 고객

- 현재 주문 상태에서 가능한 행동을 알고 싶다.
- 반품비, 환불 예정금액, 회수 일정과 진행 상태를 확인하고 싶다.
- AI가 해결하지 못하면 문맥을 유지한 채 상담원에게 이관되길 원한다.

```text
주문 상세
```

## 8. 기능 요구사항

우선순위 정의:

- P0: 쇼핑몰로서 동작하기 위해 반드시 필요
- P1: 출시 직후 고객경험과 운영 효율을 위해 필요
- P2: 성장·개인화 단계에서 추가

### 8.1 공통 레이아웃 및 내비게이션

#### STORE-GNB-001 글로벌 헤더 — P0

- 로고, 카테고리, 검색, 계정, 찜, 장바구니를 제공한다.
- 장바구니 아이콘에는 총 상품 수량을 배지로 표시한다.
- 모바일에서는 검색과 메뉴를 별도 오버레이로 제공한다.
- 키보드와 스크린리더로 모든 메뉴에 접근할 수 있어야 한다.

수용 기준:

- 모든 주요 화면에서 동일한 헤더가 유지된다.
- 장바구니 변경 후 새로고침 없이 배지가 갱신된다.
- 모바일 메뉴를 열면 포커스가 메뉴 안에 유지되고 닫으면 원래 버튼으로 돌아간다.

#### STORE-FOOTER-001 푸터 및 사업자 정보 — P0

- 상호, 대표자, 사업장 주소, 고객센터 연락처, 이메일, 사업자등록번호를 표시한다.
- 이용약관, 개인정보처리방침, 배송 및 반품 정책 링크를 제공한다.
- 실제 배포 전 통신판매업 신고 정보와 호스팅 제공자 정보의 필요 여부를 법무 검토한다.

### 8.2 홈

#### STORE-HOME-001 홈 콘텐츠 — P0

- 핵심 프로모션 Hero
- 주요 카테고리
- 신상품
- 베스트 상품
- 에디터 추천
- 배송·반품 정책 요약
- AI 고객지원 진입점

수용 기준:

- 모든 상품 카드는 상품 상세로 이동한다.
- 품절 상품은 품절 상태를 표시하고 구매 CTA를 비활성화한다.
- 배너 이미지에는 대체 텍스트가 존재한다.

#### STORE-HOME-002 개인화 영역 — P2

- 최근 본 상품, 찜 기반 추천, 재구매 추천을 제공한다.
- 로그인하지 않은 사용자는 브라우저 기반 최근 본 상품만 제공한다.

### 8.3 카테고리·상품 목록

#### STORE-PLP-001 상품 목록 — P0

- 상품 이미지, 브랜드, 상품명, 정상가, 판매가, 할인율, 리뷰 평점·수, 품절 여부를 표시한다.
- 페이지네이션 또는 접근 가능한 더보기 방식을 사용한다.
- 정렬: 추천순, 신상품순, 낮은 가격순, 높은 가격순, 리뷰순.

#### STORE-PLP-002 필터 — P0

- 카테고리, 가격 범위, 브랜드, 색상, 사이즈, 재고 있음, 할인 여부를 제공한다.
- 활성 필터를 칩으로 표시하고 개별 제거 및 전체 초기화가 가능해야 한다.
- URL query string에 검색·필터·정렬 상태를 보존한다.
- 뒤로가기로 목록 상태와 스크롤 위치를 복원한다.

#### STORE-PLP-003 빈 상태 — P0

- 결과가 없을 때 필터 초기화, 맞춤법 확인, 추천 카테고리를 제안한다.
- 단순히 “상품 없음”만 표시하지 않는다.

### 8.4 검색

#### STORE-SEARCH-001 통합 검색 — P0

- 상품명, 브랜드, 카테고리, 태그를 검색한다.
- 입력 중 추천 검색어와 상품 미리보기를 제공한다.
- 한글 초성 검색, 띄어쓰기 차이, 일반적인 오타를 허용한다.
- 최근 검색어는 사용자 기기에 저장하고 개별·전체 삭제를 제공한다.

#### STORE-SEARCH-002 검색 분석 — P1

- 검색어, 결과 수, 클릭 상품, 구매 전환 여부를 이벤트로 기록한다.
- 무결과 검색어를 운영자가 확인할 수 있어야 한다.

### 8.5 상품 상세

#### STORE-PDP-001 상품 기본 정보 — P0

- 이미지 갤러리와 확대 보기
- 브랜드, 상품명, SKU
- 정상가, 판매가, 할인율
- 옵션별 재고

### 8.10 결제

#### STORE-PAY-001 결제 요청·승인 — P0

- 초기 구현은 토스페이먼츠 테스트 환경을 기준으로 한다.
- 클라이언트는 결제창을 요청하고 서버는 결제 승인만 수행한다.
- 결제 요청 전 서버에 order_id와 확정 금액을 저장한다.
- 성공 redirect의 paymentKey, orderId, amount를 서버 저장값과 대조한다.
- 검증에 성공한 경우에만 서버에서 결제 승인 API를 호출한다.
- Secret Key는 브라우저에 포함하지 않는다.

#### STORE-PAY-002 결제수단 — P0

- 카드와 간편결제를 우선 지원한다.
- 무통장입금·가상계좌는 입금 대기 상태와 만료 처리가 준비된 후 P1에서 지원한다.

#### STORE-PAY-003 결제 상태 — P0

```text
READY → AUTHENTICATED → PAID
  ├── FAILED
  ├── CANCELLED
  └── PARTIALLY_REFUNDED → REFUNDED
```

- 결제 상태 변경은 서버 이벤트와 PG 조회 결과를 기준으로 한다.
- 새로고침과 뒤로가기로 결제가 중복 승인되지 않아야 한다.
- 타임아웃 시 “실패”로 단정하지 않고 결제 조회 후 상태를 결정한다.

#### STORE-PAY-004 실패 복구 — P0

- 사용자 취소, 한도 초과, 인증 실패, 네트워크 오류를 구분 가능한 고객 메시지로 변환한다.
- 실패 화면에서 주문서로 돌아가 다른 수단으로 다시 결제할 수 있다.
- 내부 PG 오류 원문과 키는 고객에게 노출하지 않는다.

### 8.15 AI 고객지원 및 문의 이력

#### STORE-CS-001 AI 채팅 진입 — P0

- 모든 화면에서 채팅을 열 수 있다.
- 주문 상세에서 열면 order_id를 자동 연결한다.
- 상품 상세에서 열면 product_id와 선택 옵션을 자동 연결한다.
- 사용자는 연결된 주문·상품을 확인하고 변경할 수 있다.

#### STORE-CS-002 대화 저장 — P0

- 첫 메시지 전송 시 inquiry와 conversation을 생성한다.
- 모든 메시지는 role, content, timestamp, model, prompt_version, trace_id를 저장한다.
- 고객에게는 메시지와 처리 상태만 보이고 내부 프롬프트와 Trace ID는 노출하지 않는다.
- 마이페이지 문의 내역에서 이전 대화를 다시 볼 수 있다.

#### STORE-CS-003 AI 답변 규칙 — P0

- 허용 데이터: 고객 본인의 주문, 공개 상품 정보, 승인된 정책 문서.
- 금지 행동: 임의 환불 승인, 임의 보상 확정, 타 고객 주문 조회, 확인되지 않은 배송일 생성.
- 답변에 사용한 주문 상태와 정책 버전을 서버 로그에 기록한다.
- 개인정보는 OpenRouter 및 Langfuse 전송 전에 최소화·마스킹한다.

#### STORE-CS-004 상담원 이관 — P0

- 환불 승인, 개인정보 유출, 분쟁, 반복 실패, 고객 요청 시 이관한다.
- 이관 시 고객이 내용을 다시 설명하지 않도록 주문·대화 요약을 함께 전달한다.
- 상태: RECEIVED → AI_PROCESSING → AUTO_RESOLVED 또는 ESCALATED → RESOLVED.
- 고객에게 예상 응답 시간과 현재 상태를 표시한다.

#### STORE-CS-005 고객 피드백 — P1

- AI 답변에 도움됨/도움 안 됨을 수집한다.
- 피드백을 Langfuse score와 inquiry에 모두 연결한다.
- 부정 피드백에는 추가 설명 또는 상담원 연결을 제안한다.

### 8.16 정책·법적 고지 — P0

- 초기 화면과 푸터에 사업자 신원 정보를 쉽게 확인할 수 있게 표시한다.
- 계약 전에 상품 가격, 배송비, 지급 방법·시기, 공급 방법·시기, 청약철회 조건을 고지한다.
- 주문 확정 전 주문 내용을 확인·수정·취소할 수 있어야 한다.
- 주문 완료 후 계약 내용을 이메일 또는 마이페이지에서 보존·열람할 수 있게 한다.
- 원칙적으로 상품 공급일 또는 계약서면 수령일을 기준으로 7일 청약철회 흐름을 지원하되 상품 유형과 훼손·사용 등 예외를 정책 엔진으로 관리한다.

## 9. 상태 모델

### 9.1 주문 상태

```text
PENDING_PAYMENT
├── PAYMENT_FAILED
├── CANCELLED
└── PAID
    ├── PREPARING
    │   ├── CANCEL_REQUESTED → CANCELLED
    │   └── SHIPPED
    └── SHIPPED → IN_TRANSIT → DELIVERED
                               ├── RETURN_REQUESTED
                               ├── EXCHANGE_REQUESTED
                               └── PURCHASE_CONFIRMED
```

표시용 상태와 내부 상태를 분리한다. 예: 내부 `IN_TRANSIT`은 고객에게 “배송 중”으로 표시한다.

```text
REQUESTED
→ APPROVED
→ PICKUP_SCHEDULED
→ PICKED_UP
→ INSPECTING
→ REFUND_REQUESTED
→ REFUNDED
```

거절 또는 보완이 필요한 경우 `REJECTED`, `ACTION_REQUIRED`, `WITHDRAWN`을 사용한다.

### 9.3 문의 상태

```text
RECEIVED
→ AI_PROCESSING
→ AUTO_RESOLVED
   또는 ESCALATED → AGENT_PROCESSING → RESOLVED
```

## 13. 비기능 요구사항

### 13.1 성능

- 모바일 p75 기준 Core Web Vitals 목표:
  - LCP ≤ 2.5초
  - INP ≤ 200ms
  - CLS ≤ 0.1
- 상품 이미지는 AVIF/WebP, 반응형 srcset, 지연 로딩을 사용한다.
- 첫 화면 핵심 이미지는 지연 로딩하지 않고 우선순위를 부여한다.
- 검색·필터 응답은 p95 500ms 이내를 목표로 한다.

기준: https://web.dev/articles/vitals

### 13.2 접근성

- WCAG 2.2 AA를 목표로 한다.
- 키보드만으로 구매·문의 전체 흐름을 완료할 수 있어야 한다.
- 색상만으로 상태를 전달하지 않는다.
- 폼 오류를 필드와 연결하고 오류 요약을 제공한다.
- 동적 장바구니·결제 상태 메시지는 보조기기에 전달한다.

기준: https://www.w3.org/TR/WCAG22/

### 13.3 반응형

- 기준 뷰포트: 360px, 768px, 1280px, 1440px.
- 모바일에서 고정 CTA가 콘텐츠와 키보드를 가리지 않아야 한다.
- 모바일 결제 입력에서 적절한 input type과 autocomplete을 제공한다.

### 13.4 보안

- HTTPS만 사용하고 보안 쿠키에 Secure, HttpOnly, SameSite를 설정한다.
- 인증·결제·쿠폰·재고는 서버를 신뢰 기준으로 삼는다.
- CSRF, XSS, SQL Injection, IDOR를 테스트한다.
- 결제 Secret과 OpenRouter/Langfuse Secret은 서버 환경변수에만 저장한다.
- 로그인, 결제, 쿠폰, 문의 API에 rate limit을 적용한다.
- 로그에 비밀번호, 결제 인증정보, 전체 주소·전화번호를 남기지 않는다.

### 13.5 신뢰성

- 주문·결제 webhook은 중복·순서 뒤바뀜을 허용하도록 멱등 처리한다.
- 외부 배송·결제 시스템 장애 시 재시도 큐와 수동 복구 경로를 제공한다.
- 주문과 결제 상태 불일치 탐지 작업을 주기적으로 수행한다.

### 13.6 SEO

- 홈 → 카테고리 → 하위 카테고리 → 상품이 실제 링크로 연결되어야 한다.
- canonical, sitemap.xml, robots.txt를 제공한다.
- 품절 상품의 유지·리디렉션 정책을 정의한다.
- Product, BreadcrumbList, Organization 구조화 데이터를 제공한다.

기준: https://developers.google.com/search/docs/specialty/ecommerce/help-google-understand-your-ecommerce-site-structure

## 17. 출시 수용 시나리오

1. 비회원이 모바일에서 상품을 검색하고 옵션을 선택해 테스트 결제를 완료할 수 있다.
2. 결제 직전 가격을 조작하면 서버가 승인을 거부하고 주문이 생성되지 않는다.
3. 두 사용자가 마지막 재고 1개를 동시에 구매해도 하나의 주문만 승인된다.
4. 결제 승인 응답을 새로고침해도 중복 주문·중복 승인이 발생하지 않는다.
5. 회원이 주문 상세에서 배송 상태와 예상일을 확인한다.
6. 상품 준비 상태에서는 취소를 신청하고 배송 중에는 반품 안내를 받는다.
7. 배송 완료 상품의 반품을 신청하면 반품비와 환불 예정금액이 먼저 표시된다.
8. 주문 상세에서 AI에게 배송을 문의하면 해당 주문 정보가 자동 연결된다.
9. AI 대화가 inquiry와 message로 저장되고 Ops Console과 Langfuse에서 같은 요청을 찾을 수 있다.
10. 상담원 이관 시 주문 정보와 전체 대화가 함께 전달된다.
11. 다른 사용자의 주문번호를 URL에 입력해도 주문 정보가 노출되지 않는다.
12. 키보드와 스크린리더만으로 상품 선택부터 주문 완료까지 진행할 수 있다.
