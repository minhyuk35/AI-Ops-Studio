일일 리포트에 JSON 필드명·(null) 노출 daily-seller-report 페르소나 프롬프트 오해로 gross_revenue/order_count 같은 필드명과 (null)이 판매자 화면에 그대로 노출되던 문제 — Langfuse에서 새 버전(v2)을 발행해 production 라벨 이동, JSON 문법·null 노출 금지 규칙 추가
✓
상품 등록/수정 폼 레이아웃 로그인 폼용 좁은 단일 컬럼 클래스를 재사용하고 있던 것을, 체크아웃·회원가입과 같은 2열 .form-grid로 전환(720px). 취소·등록 버튼을 폼 하단에 짝으로 배치

A-9검색·개인화·추천 캐시 + 리뷰·쿠폰·업로드·번들 최적화

이전 B-1/B-2 로드맵 항목 다수를 실제로 구현했습니다(사이즈 프로필, 검색 개선, 추천 캐시 테이블, 파일 업로드, 번들 최적화) — 리뷰·쿠폰은 기획에 없던 신규 기능입니다.

✓
검색 토큰 기반 다중 매칭 q 파라미터를 공백 기준 최대 6개 토큰으로 나눠, 각 토큰이 상품명·브랜드·설명·카테고리명 중 하나에라도 매칭돼야 하는 AND 조건으로 전환(기존엔 단일 문자열 LIKE만 가능)
✓
사이즈 프로필 개인화 별도 프로필 테이블 없이 order_items.option_text("{color} / {size}")를 파싱해 고객별·대분류별 최다 구매 사이즈를 즉시 계산 — 재고 있는 사이즈와 일치하면 추천 점수 +6.0 가산, preferred_size_match로 응답에 노출
✓
product_affinity 캐시 테이블 전환 A-3에서 실시간 계산으로 남겨뒀던 부분을 실제 캐시 테이블로 전환 — 상품 태깅/수정 시 O(N), 새 조합 신호 발생 시 O(1)로 증분 갱신하고, 테이블이 비어있으면(최초 1회) 지연 전체 백필. 캐시 미스 시엔 기존 실시간 계산으로 폴백
✓
리뷰 작성 기능 배송 완료된 주문에 실제로 포함된 상품에 한해 구매자당 상품별 1개 리뷰 작성 가능(reviews 테이블, UNIQUE(customer_id, product_id)) — 첫 실제 리뷰가 등록되면 시드로 넣어둔 고정 평점·리뷰수를 실제 AVG/COUNT로 완전히 대체
✓
쿠폰 시스템 하드코딩돼 있던 WELCOME10 한 줄짜리 체크를 실제 coupons 테이블(퍼센트/정액, 최대 할인, 최소 구매 금액, 만료일)로 일반화. 총관리자 콘솔에 생성·활성화 토글 UI 신설, 쿠폰이 생성되면 소비자가 사이트 접속 시 안내 팝업을 보고, 한 번 닫은 쿠폰은 localStorage에 기록돼 다시 뜨지 않음(단, 새 쿠폰이 생기면 그건 다시 뜸)
✓
Vercel Blob 파일 업로드 브라우저 → FastAPI 백엔드(멀티파트) → Vercel Blob REST API로 서버 사이드 업로드. BLOB_READ_WRITE_TOKEN이 없으면 GET /uploads/status가 enabled:false를 반환해 업로드 버튼 자체가 자동으로 숨겨지고 URL 입력만 노출(그레이스풀 디자인)
✓
번들 사이즈 최적화 SellerConsolePage/AdminConsolePage를 별도 모듈로 분리해 React.lazy로 지연 로드 — 소비자는 이제 이 코드를 아예 받지 않음. 여기에 vite.config.ts의 manualChunks로 react/gsap/react-markdown 벤더 청크를 분리해 Vite 500KB 경고 해소(진입 청크 gzip 170KB → 90KB)

이 프로젝트엔 BLOB_READ_WRITE_TOKEN이 아직 없어서 Vercel Blob 실제 업로드 호출은 라이브로 검증하지 못했습니다 — 토큰 연결 방법은 참고.

★가상 피팅 (웹캠 실시간 착장) — 교수님 피드백 로드맵

교수님 피드백 ② · 아직 미구현 · 계획 수립 완료

"카메라로 옷을 골라 입어본 것처럼 실시간으로 움직이는 가상 피팅." 현재 코드베이스에 카메라/웹캠 기능은 어떤 형태로도 없습니다(의존성도 없음). 기존 스택(FastAPI + React, LLM 오케스트레이션)과 거의 겹치지 않는 별도의 컴퓨터비전/AR 서브시스템이라 별도 스프린트로 남겨두고, 아래처럼 컴퓨터 웹캠 기준 단계별 계획을 세웠습니다.

왜 별도 서브시스템인가

지금 프로젝트의 핵심은 LLM 페르소나 오케스트레이션과 백엔드 데이터 처리입니다. 가상 피팅은 브라우저 안에서 도는 실시간 CV 모델 추론 + WebGL 렌더링 + 상품별 의류 에셋 파이프라인이라, 서버 API를 하나 더 붙이는 문제가 아니라 프런트엔드에 완전히 새로운 실시간 처리 계층을 얹는 작업입니다.

기술 스택 (웹캠 기반 · 전부 브라우저 내 처리)

계층선택 기술역할
카메라 입력getUserMedia (WebRTC) + <video>컴퓨터 웹캠 스트림 확보(권한 요청)
실시간 포즈 추정MediaPipe Pose / BlazePose (TF.js)어깨·골반·팔 등 33개 랜드마크를 프레임마다 추적
인물 분리(2단계~)MediaPipe Selfie Segmentation사람과 배경 분리 → 옷을 몸에만 겹침
의류 합성1단계 Canvas 2D 워핑 → 2단계 WebGL/Three.js상품 이미지를 랜드마크에 맞춰 스케일·회전·워핑
렌더 루프<canvas> + requestAnimationFrame웹캠 프레임 위에 착장 오버레이 실시간 렌더
상품 에셋투명 배경 착장 PNG(1단계) → 3D 의류 메쉬(4단계)상품별 피팅용 에셋 제작 파이프라인 필요

단계별 구현 계획

0
PoC — 웹캠 + 포즈 오버레이 웹캠 권한을 받아 <video>를 띄우고, MediaPipe Pose로 잡은 골격 랜드마크를 캔버스에 그려 "실시간 추적이 된다"만 확인. 상품 없음.
1
2D 오버레이 착장 (MVP) 상의 상품의 투명 PNG를 어깨 두 랜드마크 기준으로 스케일·회전·위치 맞춰 얹기(정면 기준). 상품 상세의 "가상 피팅" 버튼 → 모달로 웹캠 착장.
2
세그멘테이션 + 사이즈 연동 Selfie Segmentation으로 인물을 분리해 옷이 배경이 아니라 몸에만 겹치게. 기존 사이즈 프로필(구매 이력 기반)과 연동해 "추천 사이즈"를 함께 표시.
3
앞/뒤 레이어링 · 다각도 팔이 옷 앞으로 오면 가려지도록 깊이 레이어링, 측면 포즈 대응.
4
3D 메쉬 워핑 (고도화) Three.js로 의류를 3D 메쉬로 만들어 옷감이 움직임을 따라 자연스럽게 흔들리게(스켈레톤 바인딩·클로스 시뮬). 상품별 3D 에셋 파이프라인이 전제.

통합 지점 (기존 기능 재활용)

  • 상품 상세 페이지에 "가상 피팅" 버튼 → 웹캠 모달
  • 구매 이력 기반 사이즈 프로필과 연동해 추천 사이즈 표시
  • 피팅해 본 상품을 AI 추천 신호로 재사용(조회 이력처럼)

리스크 · 고려사항

  • 성능 — 포즈 모델 로딩(수 MB, WASM/GPU 백엔드)·프레임레이트. 저사양 기기는 정지 이미지 합성으로 폴백
  • 개인정보 — 영상은 서버로 안 보내고 브라우저 안에서만 처리(전송·저장 없음)
  • 에셋 비용 — 상품마다 피팅용 투명 PNG/3D 메쉬 제작이 필요(카탈로그 확장 시 병목)
  • 범위 — 우선 컴퓨터 웹캠 기준. 모바일 카메라는 이후 단계

·Vercel Blob 연결 가이드 (지금 바로 할 수 있는 설정)

상품 이미지 파일 업로드(A-9)는 코드가 이미 준비돼 있고, 토큰만 연결하면 바로 켜집니다.

1
Vercel 대시보드 → 이 프로젝트 → Storage 탭 Create Database → Blob 선택 → 이름 지정 후 생성
2
생성된 Blob 스토어를 프로젝트에 Connect BLOB_READ_WRITE_TOKEN이 Production/Preview/Development 환경변수에 자동으로 추가됨
3
재배포 POST /api/commerce/sellers/me/uploads(판매자 인증 필요, JPEG/PNG/WEBP/GIF, 4MB 이하)가 파일을 Blob에 업로드하고 URL을 반환 — 판매자 콘솔 상품 등록 폼에 "파일 업로드" 버튼이 자동으로 나타남
4
로컬에서 켜고 싶으면 Blob 스토어의 .env.local 다운로드 버튼으로 토큰을 받아 .env(커밋 금지)에 추가

아직 실제 호출로 검증 못 함

토큰이 없어서 Vercel Blob REST API 실제 응답 형태(헤더 이름 등)는 라이브로 확인하지 못했습니다 — 토큰 연결 후 상품 등록 화면에서 실제 파일 업로드 한 번 테스트해보세요. 자세한 내용은 저장소 루트의 DEPLOYMENT.md에도 같은 내용이 있습니다.

B-4알려진 기술 부채

REFUND_NEGATIVE 신호의 정확도 한계

이 프로젝트의 반품/환불 데이터 모델이 주문 단위라(어떤 특정 품목이 반품됐는지 추적 안 함), 여러 상품을 같이 산 주문이 환불되면 그 주문 안의 모든 상품 쌍에 REFUND_NEGATIVE가 적용됩니다. 품목 단위 반품 추적을 추가하면 해결 가능하지만 클레임 데이터 모델 자체를 확장해야 함.

mypy 기존 미해결 에러 다수 (신규 아님)

services/mock-commerce-api·core-api 양쪽에 Row/object 인덱싱 관련 mypy 에러가 100건 이상 있으나, 전부 프로젝트 전반의 기존 컨벤션이라 손대지 않았습니다. 언젠가 타입 정리 작업을 한 번 몰아서 하는 게 좋습니다.

카테고리 시드 드리프트 (2026-08-06에 발견 · 정리 완료)

프로덕션 DB의 categories 테이블이 예전 버전의 taxonomy(같은 slug, 다른 id)를 그대로 갖고 있었는데, 카테고리 재시드 로직이 "카탈로그가 이미 시드됨" 체크 뒤에 같이 묶여 있어서 한 번 시드된 뒤로는 조용히 다시 실행되지 않고 있었습니다 — 그래서 몇 년째 드리프트가 안 보였던 것. 이번 프로덕션 정리로 상품과 함께 카테고리도 비우고 재시드해서 해소했지만, 카테고리 구조를 또 바꿀 일이 생기면 ON CONFLICT(id) upsert 특성상 같은 문제가 재발할 수 있음을 기억해둘 것.
