The One Principle

숫자는 SQL이 계산하고, AI는 해석만 한다

# 절대 금지: LLM이 매출·환불 숫자를 "생성"하는 것
raw events  ──SQL 집계──▶  확정 숫자(dict)  ──프롬프트 변수 주입──▶  LLM 해석 텍스트
  • 판매·환불 이벤트마다 LLM을 부르지 않는다. 정확히 누적·집계한 뒤 정해진 시점에 집계 dict만 AI에 넘긴다 → 분석 비용 ↓, 환각 위험 ↓.
  • 모든 페르소나 프롬프트에 “숫자를 다시 계산하지 말고 해석만 하라”는 규칙이 명시돼 있다.
  • 덕분에 리포트는 재현 가능: 같은 input_snapshot + 같은 prompt_version = 같은 근거.
Data · Event Ledger

모든 것의 원천: commerce_events

매출·환불·조회는 상태값이 아니라 불변 이벤트 로그로 쌓인다. 집계는 “지금 주문 상태”가 아니라 이벤트 발생 시점(occurred_at) 기준이라, 다음 달 들어온 환불이 이번 달 매출을 덮어쓰지 않는다.

멱등성(idempotency)

external_event_id = UNIQUE
# 재시도로 같은 취소가 두 번 와도
INSERT OR IGNORE → 매출·환불 이중 집계 방지

예: {order_id}:PAYMENT_CONFIRMED, {order_id}:{variant}:STOCK_CHANGED:ORDER_CREATED

이벤트 타입 7종

event_type언제
PRODUCT_VIEWED상품 상세 조회
ORDER_CREATED주문 생성
PAYMENT_CONFIRMED결제 승인(매출 인식)
STOCK_CHANGED재고 증감(±수량)

각 이벤트엔 org_id가 붙어 판매자별 집계가 가능하다.

Formulas · 1/3 · analytics.revenue_summary()

매출 요약 수식

gross_revenue = Σ amount  where event_type = PAYMENT_CONFIRMED
refund_amount = Σ refund_amount  where event_type = REFUND_COMPLETED
net_revenue  = gross_revenue − refund_amount
order_count  = COUNT(DISTINCT order_id)  where PAYMENT_CONFIRMED
average_order_value = net_revenue // order_count  # order_count=0이면 0

기간 경계 _month_bounds("YYYY-MM") → [start, end) 반개구간. 모든 합계는 COALESCE(…, 0)로 NULL을 0으로 만들어 빈 기간에도 안전.

def revenue_summary(connection, period) -> dict:
    start, end = _month_bounds(period)   # [start, end)

Formulas · 2/3 · 증감률 · 환불률

비교 지표의 안전장치

전월 대비 증감률

pct = round( (curr − prev) / prev × 100, 1 )
# prev == 0 이면?
→ None  # 0을 기준으로 한 성장률은 정의 불가 → 지어내지 않음

_percent_change(current, previous). 4개 지표(gross/net/order/AOV)에 각각 적용.

상품별 환불률(표본 보정)

refund_rate = refund_units / units_sold
# units_sold == 0 이면 None (이번 달 판매 0)
# 판매 < 3 이면 프롬프트가 "표본 적음" 경고

지난달 산 걸 이번 달 환불하면 units_sold=0 → 무한대/0나눗셈 대신 None. 코호트 기반 환불률은 아직 미구현(한계 슬라이드 참고).

원칙: 불확실하면 숫자를 만들지 않고 None으로 비운다. LLM은 이 None을 “비교 불가”로 서술한다.

Formulas · 3/3 · 플랫폼 매출 · 점유율

“판매자 매출”이 아니라 “플랫폼 매출”

commission_revenue = round( seller_gross × commission_rate )
plan_fee = PLAN_MONTHLY_FEES[plan]
platform_contribution = commission_revenue + plan_fee
total_platform_revenue = platform_default_revenue + Σ platform_contribution
share_pct = round( platform_contribution / total_platform_revenue × 100, 1 )

플랜 월 요금 PLAN_MONTHLY_FEES

FREE 0원 BASIC 35,000 PRO 150,000 BUSINESS 300,000

핵심 통찰: 판매액(GMV)이 커도 무료 플랜이면 플랫폼 기여도는 낮을 수 있다. 그래서 seller-market-share 페르소나는 gross_revenue와 platform_contribution을 혼동하지 말라고 못박는다.

Langfuse · 개념

프롬프트를 코드 밖으로 꺼낸다

  • name — 작업·페르소나의 식별자 (예: customer-support-answer)
  • label = production — 지금 실제로 돌 버전을 가리키는 포인터
  • config — model · temperature · max_tokens · provider.*가 프롬프트에 함께 저장 → 코드에 하드코딩 없음
  • composability — 공통 말투/안전 규칙 sub-prompt를 재사용(페르소나 수엔 미포함)
  • fallback — Langfuse 불가 시 personas.py의 로컬 프롬프트 + OPENROUTER_DEFAULT_MODEL

모델 교체 = 재배포 없음

새 prompt version에서 config.model 변경
↓
production 라벨을 새 버전으로 이동
↓
최대 prompt cache TTL(기본 300s) 뒤 반영

안전장치: config의 gateway가 "openrouter"가 아니면 코드가 ValueError를 던져 엉뚱한 비밀값 사용을 막는다.

End-to-End · 가장 중요한 경로

문의 한 건이 흐르는 전 구간

0 · 진입 POST /api/v1/inquiries — OpenRouterSupportService.answer(request)
1 · Trace 시작 langfuse.start_as_current_observation(...) · trace_id = create_trace_id(seed=request_id)
2 · Triage span _triage() → compile(name=langfuse_triage_prompt_name) → JSON(category·risk·requires_human) → TriageResult
3 · Retrieve span retrieve-support-prompt → PromptRepository.compile(name=langfuse_support_prompt_name, label=production) · 변수 치환
4 · Config 결정 merged = {…FALLBACK_CONFIG, …prompt.config} → model·temperature·max_tokens·provider
5 · Generation _generate_with_openrouter(request, compiled) → langfuse.openai.OpenAI가 OpenRouter 호출 + 자동 추적
6 · 응답 처리 choices[0].message.content=답변 · completion.model=실제 사용 모델(fallback 시 요청과 다를 수 있음)
7 · 이관 판정 requires_human → Ops Console 에스컬레이션 + DiscordNotifier로 알림

면접 대비 한 줄 요약: “분류하고 → 프롬프트 버전 가져오고 → config로 모델 정하고 → OpenRouter로 생성하고 → 위험하면 사람에게 넘긴다.”

OpenRouter · 호출 상세

_generate_with_openrouter() 안에서

# llm_client.build_openrouter_client(settings) — Langfuse가 감싼 OpenAI SDK
from langfuse.openai import OpenAI
client = OpenAI(base_url=OPENROUTER_BASE_URL, api_key=OPENROUTER_API_KEY)

completion = client.chat.completions.create(
    model       = compiled.config["model"],        # 예: ~google/gemini-flash-latest
    temperature = compiled.config["temperature"],  # 페르소나별 0~0.3
    max_tokens  = compiled.config["max_tokens"],
    messages    = [{"role":"user", "content": compiled.text}],
    extra_body  = {"provider": {"allow_fallbacks":True, "data_collection":"deny"}},
    langfuse_prompt = compiled.langfuse_prompt,   # generation ↔ prompt version 링크
)
allow_fallbacks 1차 provider 장애 시 자동 대체 data_collection=deny 학습 미사용 경로만 reasoning.effort=none 리포트 잘림 방지

애플리케이션 레벨 재시도는 없음 — provider fallback과 별개로 호출 자체가 예외를 던지면 그대로 실패(한계 슬라이드).

Persona 상세 · daily-seller-report

판매자 일일 리포트의 하이라이트 계산

seller_daily_snapshot(org_id, date)가 상품별 조회·판매·환불·재고를 한 번에 뽑고, 코드가 하이라이트를 미리 계산해 넘긴다. LLM은 그대로 인용만.

most_viewed = max(products, key=views)
least_viewed = min(products, key=views)
most_purchased = max(·, key=units_sold)
out_of_stock = [p for p if stock == 0]
low_stock = [p for p if 0 < stock ≤ 3]

프롬프트 규칙

  • 순서 고정: 오늘 요약 / 많이·적게 본 상품 / 많이 팔린·환불된 상품 / 재고
  • 조회수 높은데 재고 부족·0인 상품은 반드시 짚기
  • “AI 제안”에서 어떤 상품을 왜 채워야 하는지 구체 제안
  • 원인 단정 금지 → “~로 추정됩니다”

이 리포트가 판매자 Discord 일일-리포트 채널로 간다(플랜 무관 기본 제공).

  • trace = 문의/리포트 1건 (seed로 trace_id 고정 → 재현)
  • span = triage · retrieve-support-prompt 등 단계
  • generation = LLM 호출(모델·토큰·지연·prompt_version 자동 기록)
  • propagate_attributes로 session/user 연결

Delivery · Discord

리포트를 Discord로 — 2000자 청킹

DiscordNotifier.send()는 절대 예외를 던지지 않는다(알림 실패가 AI 파이프라인을 죽이면 안 됨). AI 리포트는 자주 2000자를 넘겨서 _chunk_content()가 문단 경계로 나눠 순차 전송.

def _chunk_content(content, max_length=2000):
    while len(remaining) > max_length:
        window = remaining[:max_length]
        split = window.rfind("\n\n")        # 1순위: 문단 경계
        if split == -1: split = window.rfind("\n") # 2순위: 줄 경계
        if split == -1: split = max_length     # 3순위: 강제 절단
        chunks.append(remaining[:split].rstrip())
        remaining = remaining[split:].lstrip("\n")

두 개의 독립 노티파이어: DISCORD_WEBHOOK_URL(판매자·이관) vs ADMIN_DISCORD_WEBHOOK_URL(관리자 전용) — 관리자 정보가 판매자 채널로 새지 않도록 물리적으로 분리.

신규 · 판매자 Discord 봇

봇이 “판”을 깔고, 노트북 AI가 “발신”한다

1 · 링크코드 발급 판매자 콘솔 → POST /sellers/me/discord/link-code → organizations.discord_link_code
2 · 봇 초대 후 /연동 <코드> 봇 → POST /internal/discord/link {guild_id, code} → guild ↔ org 바인딩
3 · /생성 봇 → GET /internal/discord/org(플랜별 채널 스펙) → 카테고리·채널 생성 + channel.create_webhook()
4 · 웹훅 저장 봇 → PUT /internal/discord/channels → discord_channels(webhook_url)
5 · 노트북 AI 발신 노트북이 저장된 웹훅 URL로 페르소나별 리포트 전송(AI는 내 노트북에서)

봇 지표 명령(/수익 /조회수 /일일리포트 /재고)은 GET /internal/discord/metrics로 SQL 집계 숫자만 가져온다 — 여기서도 AI는 숫자를 만들지 않는다.

Data · SQLite ↔ Postgres

같은 SQL, 두 백엔드 — 실행 시점 번역

로컬·테스트는 SQLite, DATABASE_URL이 postgres(ql)://면 psycopg로 Neon 연결. 호출부는 백엔드를 신경 쓰지 않고, _rewrite_sql()이 실행 직전 문장을 번역한다.

INSERT OR IGNORE → INSERT … ON CONFLICT DO NOTHING
LIKE → ILIKE  # SQLite 기본 대소문자 무시 유지
:param → %(param)s    ? → %s

PostgresConnection이 execute/executemany/executescript 표면을 sqlite3와 동일하게 맞춰, 같은 코드가 두 DB에서 돈다. 주의: 이 경로는 라이브 Postgres로 광범위 검증 전제가 아님(문서 참고).

요약

한 문장으로

사용자의 행동은 멱등한 이벤트가 되고, SQL이 그것을 확정 숫자로 집계하며, 그 숫자는 “누가 보는가”에 따라 서로 다른 Langfuse name의 페르소나로 해석되어, OpenRouter를 거쳐 Langfuse에 추적되고, Discord(봇이 판 채널·웹훅)로 전달된다. AI는 끝까지 숫자를 만들지 않고 해석만 한다.

숫자 = SQL 해석 = 페르소나 추적 = Langfuse 전달 = Discord 재현 = trace_id + prompt_version
