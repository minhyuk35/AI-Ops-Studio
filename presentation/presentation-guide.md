# AI Ops Studio · 발표 진행 가이드 + 예상 질문 답변

`ai-flow-deck.html`(30장, 브라우저에서 열고 `←`/`→`로 넘기고 `N`으로 슬라이드별 발표 대본 확인 가능)을
실제로 발표할 때 쓰는 보조 자료입니다. 이 파일 자체는 화면에 띄우는 게 아니라, 발표 전에 읽고 준비하는 대본 + 예상 질문 노트입니다.

## 1. 전체 진행 가이드

### 1.1 발표 골격 (30장, 약 20~25분 기준)

| 구간 | 슬라이드 | 시간 배분 | 목표 |
|---|---|---|---|
| 오프닝 | 1~2 | 1분 | 오늘 무슨 얘기를 하는지, 핵심 원칙 한 줄 예고 |
| Ⅰ. 뼈대 | 3~8 | 4분 | 시스템 지도 → 스택 → 핵심 원칙(숫자=SQL, 해석=AI) → 이벤트 원장 |
| Ⅱ. AI 파이프라인 | 9~16 | 6분 | Langfuse 개념 → 7개 페르소나 → 문의 응대 End-to-End (가장 중요한 구간) |
| Ⅲ. 전달·운영 | 17~21 | 4분 | 트레이싱 → 스케줄 → Discord 전달 → 디스코드 봇 연동 |
| Ⅳ. 구현 상세 (신규) | 22~27 | 5분 | 인증 · DB 이중 백엔드 · 봇 2가지 실행 방식 · 프런트 · 배포 · 실전 트러블슈팅 |
| 마무리 | 28~30 | 2분 | 보안 총람 → 한계 솔직 인정 → 한 문장 요약 |

시간이 빠듯하면 **9~16번(AI 파이프라인)과 27번(트러블슈팅)은 절대 스킵하지 마세요** — 이 두 구간이
"이 사람이 실제로 이해하고 만들었는가"를 가장 잘 보여줍니다. 시간이 없으면 4번(스택), 21번(플랜→채널)을 줄이세요.

### 1.2 톤 원칙

- **자랑하지 말고 설명하라.** "이렇게 잘 만들었습니다"가 아니라 "이 문제 때문에 이렇게 할 수밖에 없었습니다"로 말하기.
  예: "숫자를 SQL로 계산하는 이유는, LLM에게 집계까지 맡기면 같은 질문에 다른 숫자가 나올 수 있어서입니다."
- **매 파트 전환마다 "왜"를 먼저 던지고 답하는 구조.** 슬라이드 대본이 이미 이 구조로 쓰여 있습니다 (예: "왜 sha256을 먼저 거치나").
- **모르는 질문에는 추측하지 말고 "확인 후 답변드리겠습니다"라고 말하기.** 이 프로젝트는 한계 슬라이드(29번)에서
  스스로 부족한 점을 먼저 밝히기 때문에, 모른다고 인정하는 게 오히려 신뢰를 깎지 않습니다.
- **27번 트러블슈팅 슬라이드는 발표의 클라이맥스로 취급하세요.** 이론이 아니라 실제로 오늘 겪고 고친 버그라서
  가장 설득력이 강합니다. 여기서 속도를 늦추고, "이게 왜 로컬에서는 재현이 안 됐는지"를 강조하세요.

### 1.3 슬라이드별 발화 팁 (신규 22~27번 위주)

- **22 (인증)**: 코드를 읽어주지 말고 "72바이트 넘는 비밀번호를 넣으면 bcrypt가 조용히 잘라버린다"는
  실패 시나리오부터 얘기한 다음 sha256 다이제스트로 해결했다고 설명하면 훨씬 잘 들립니다.
- **23 (DB 이중 백엔드)**: "왜 처음부터 Postgres만 쓰지 않았나?"를 스스로 먼저 던지고 답하세요 —
  "로컬 개발은 SQLite가 설치가 필요 없어 빠르고, 배포는 Postgres가 필요해서 두 경로를 하나의 인터페이스로 묶었다."
- **24 (봇 2가지 방식)**: 여기서 "오프라인으로 보이는데 왜 정상이냐"는 질문이 반드시 나옵니다.
  Gateway 세션이 없어서 그런 거고 슬래시 명령 응답에는 영향이 없다는 걸 먼저 선수 쳐서 설명하면 좋습니다.
- **27 (트러블슈팅)**: 다섯 단계를 빠르게 읽지 말고, 1차 원인을 고쳤는데 왜 안 됐는지 → 2차 원인을 고쳤는데
  왜 안 됐는지, 라는 식으로 **직접 겪은 순서 그대로** 말하세요. "됐다고 생각했는데 또 안 됐다"는 흐름이
  진짜 디버깅 경험을 보여줍니다.

### 1.4 라이브 데모를 곁들일 경우

덱만으로도 충분하지만, 시간이 되면 다음 순서를 추천합니다 (각 1분 내외):

1. 데모 스토어에서 상품 상세 페이지 조회 → (백그라운드에서 `PRODUCT_VIEWED` 이벤트가 쌓였다고 설명)
2. 판매자 콘솔의 "오늘의 데이터" 대시보드 열기 → 코드가 집계한 숫자 + AI 해석이 같이 보이는 걸 보여주기
3. "Discord로 전송" 버튼 클릭 → 실제 디스코드 채널에 리포트가 도착하는 걸 보여주기 (가장 임팩트 있는 데모)
4. (선택) 디스코드에서 `/수익` 같은 슬래시 명령 실행 → 즉시 숫자 응답

데모 전에는 반드시 사전에 한 번 리허설하세요 — 특히 3번은 네트워크·Discord 상태에 따라 몇 초 걸릴 수 있습니다.

### 1.5 마무리 멘트 예시

> "정리하면 이렇습니다.
> 사용자의 행동은 이벤트가 되고, SQL이 숫자를 확정하고, AI는 그 숫자를 누가 보느냐에 따라 다르게 해석만 합니다.
> 오늘 발표에서 가장 강조하고 싶었던 건 이 원칙 하나였고, 나머지 인증·배포·봇 같은 구현들은 전부 이 원칙을
> 안정적으로 서비스하기 위한 뒷받침이었습니다. 질문 받겠습니다."

## 2. 예상 질문 Q&A

카테고리별로 정리했습니다. 실제 면접/발표에서는 이 문장을 그대로 외우지 말고, **왜 그렇게 했는지의 핵심 이유
한 문장**만 기억해두고 나머지는 즉흥적으로 풀어도 됩니다.

### 2.1 AI / LLM 설계

**Q. 왜 OpenAI를 직접 안 쓰고 OpenRouter를 거치나요?**
A. 하나의 API로 여러 모델 제공자에 접근할 수 있고, `allow_fallbacks` 옵션으로 1차 제공자가 장애가 나면
자동으로 다른 제공자로 넘어갑니다. 특정 벤더에 종속되지 않고, 모델을 Langfuse 설정값 하나만 바꿔서
교체할 수 있다는 것도 장점입니다.

**Q. Langfuse 없이 그냥 프롬프트를 코드에 하드코딩하면 안 되나요?**
A. 됩니다만, 모델이나 temperature를 바꿀 때마다 재배포가 필요해집니다. Langfuse는 프롬프트를 버전 관리하고,
`production` 라벨을 옮기는 것만으로 즉시(캐시 TTL 이후) 반영되게 해줍니다. 또 모든 호출이 자동으로
트레이스로 남아서, "이 리포트가 왜 이렇게 나왔지"를 나중에 그대로 재현해서 확인할 수 있습니다.

**Q. LLM이 숫자를 잘못 계산해서 틀린 리포트를 보내면 어떡하나요?**
A. 그게 바로 이 프로젝트의 핵심 설계 원칙입니다 — LLM은 숫자를 계산하지 않습니다. 모든 숫자는 SQL이
먼저 확정해서 dict로 만들고, 프롬프트에는 "이 숫자를 다시 계산하지 말고 해석만 하라"고 명시돼 있습니다.
그래서 LLM이 할 수 있는 실수는 "서술을 이상하게 한다" 정도지, 숫자 자체를 틀리는 건 구조적으로 막혀 있습니다.

**Q. 프롬프트 인젝션(사용자가 "이전 지시 무시하고..."라고 입력)은 어떻게 막나요?**
A. 지금은 별도의 인젝션 탐지 레이어는 없고, `support-triage` 페르소나가 위험도를 분류해서 애매하거나
위험한 문의는 무조건 사람에게 이관하도록 되어 있습니다. 완벽한 방어는 아니고, 로드맵에 있는
"애플리케이션 레벨 재시도·검증 강화" 항목과 함께 다뤄야 할 부분이라고 솔직히 답하는 게 좋습니다.

**Q. 왜 각 용도마다 페르소나(프롬프트)를 따로 두나요? 하나로 합치면 안 되나요?**
A. 같은 숫자라도 보는 사람이 다르면(판매자 본인 vs 전체 관리자) 노출 범위와 어조가 달라야 합니다.
하나로 합치면 실수로 관리자 전용 데이터가 판매자에게 노출될 위험이 생기고, temperature 같은 설정도
분류 작업(0)과 리포트 작성(0.2~0.3)에 다르게 필요합니다. 그래서 이름·API·Discord 채널까지 물리적으로 분리했습니다.

**Q. 토큰 비용은 어떻게 관리하나요?**
A. 지금은 max_tokens을 페르소나별로 제한해두는 정도입니다 (예: 일일 리포트는 1800토큰). 프롬프트 캐싱이나
사용량 모니터링 대시보드는 아직 없고, 이 부분은 실제 운영 단계에서 Langfuse의 비용 트레이싱 기능을
더 활용해야 할 부분입니다.

### 2.2 데이터/아키텍처

**Q. 왜 "현재 상태" 테이블이 아니라 이벤트를 쌓는 방식(이벤트 소싱)을 썼나요?**
A. 상태값만 저장하면 "지금 재고가 몇 개냐"는 답할 수 있어도 "지난달 매출이 얼마였냐"는 답할 수 없습니다.
이벤트는 발생 시점이 고정돼 있어서, 이번 달에 들어온 환불이 지난달 매출을 소급해서 깎지 않습니다.
또 `external_event_id`가 유니크해서, 같은 이벤트가 중복으로 들어와도(재시도 등) 두 번 집계되지 않습니다.

**Q. 왜 core-api와 mock-commerce-api를 하나로 합치지 않고 나눴나요?**
A. mock-commerce-api는 "커머스 사실"(상품·주문·이벤트)을 소유하는 서비스고, core-api는 "AI 해석"을
담당하는 서비스입니다. 책임을 분리해서, 나중에 실제 커머스 시스템과 연동할 때 core-api 쪽만 그대로
재사용할 수 있게 하려는 의도입니다. 다만 지금은 둘 다 하나의 Vercel 배포 안에서 함께 돌기 때문에,
실질적으로는 프런트에서 두 개의 API처럼 보이지만 운영 부담은 하나입니다.

**Q. 왜 SQLite와 Postgres를 동시에 지원하나요? 처음부터 Postgres만 쓰면 안 되나요?**
A. 로컬 개발 환경에서는 SQLite가 설치·설정이 전혀 필요 없어서 개발 속도가 빠릅니다. 배포 환경(Vercel)은
서버리스라 로컬 파일시스템에 쓸 수 없기 때문에 실제 DB(Neon Postgres)가 필요합니다. `db_compat.py`가
두 백엔드를 같은 인터페이스로 감싸서, 나머지 코드는 어떤 DB를 쓰는지 신경 쓰지 않게 만들었습니다.

**Q. SQL을 정규식으로 SQLite→Postgres로 변환하는 방식, 위험하지 않나요?**
A. 네, 완벽하지 않다는 걸 알고 있고 실제로 두 가지 버그를 배포 후에 발견했습니다 —
`rowid`(SQLite 전용 암묵 컬럼)를 쓴 쿼리, 그리고 Postgres가 SQLite보다 `GROUP BY`를 더 엄격하게
검사해서 JOIN된 테이블의 컬럼을 그룹핑 목록에 명시해야 했던 경우입니다. 테스트 스위트가 SQLite로만
돌아서 이런 차이를 못 잡았고, 실제 배포 로그를 보고서야 발견했습니다. 이건 이 프로젝트의 정직한 한계입니다 —
진짜 마이그레이션이 필요하다면 정규식 치환이 아니라 ORM이나 쿼리 빌더를 쓰는 게 맞습니다.

**Q. 멱등성(idempotency)은 왜 중요한가요? 실제로 어떻게 보장하나요?**
A. 결제/이벤트 시스템은 네트워크 재시도 때문에 같은 요청이 두 번 올 수 있습니다. `commerce_events`
테이블의 `external_event_id`에 UNIQUE 제약을 걸고 `INSERT OR IGNORE`(Postgres에서는
`ON CONFLICT DO NOTHING`)로 삽입하기 때문에, 같은 이벤트가 중복으로 와도 두 번째는 조용히 무시되고
매출이 이중으로 잡히지 않습니다.

### 2.3 보안

**Q. 왜 세션이 아니라 JWT를 쓰나요?**
A. 서버가 세션 상태를 따로 저장할 필요가 없어서 서버리스 환경(Vercel Functions, 요청마다 새 프로세스일
수 있음)에 잘 맞습니다. 대신 리프레시 토큰이나 즉시 폐기(revoke) 기능은 없어서, TTL을 7일로 짧게 잡고
포트폴리오 데모 수준의 트레이드오프를 인정한 설계입니다.

**Q. 왜 core-api는 JWT를 직접 검증하지 않고 mock-commerce-api에 물어보나요?**
A. mock-commerce-api가 고객 계정의 발급자(issuer)이기 때문에, 리소스 서버 패턴을 따라서 "이 토큰이
진짜인지, 누구 건지"는 발급자에게만 묻습니다. 두 서비스가 같은 시크릿을 공유할 필요가 없어지고,
나중에 인증 방식이 바뀌어도(예: OAuth 서버 도입) core-api 코드는 안 건드려도 됩니다.

**Q. 봇 내부 API(`/internal/discord/*`)는 왜 JWT가 아니라 공유 비밀(shared secret)을 쓰나요?**
A. 이건 사람이 아니라 서비스 대 서비스(디스코드 봇 ↔ 커머스 API) 통신이라 JWT 발급/만료 관리가
오히려 과합니다. `X-Internal-Token` 헤더를 상수 시간 비교(`secrets.compare_digest`)로 검증하고,
비밀값이 비어있으면 전부 401을 던지는 fail-closed 기본값을 씁니다.

**Q. 비밀번호를 sha256으로 먼저 해싱하고 bcrypt를 또 쓰는 게 이중 해싱 아닌가요, 안전한가요?**
A. bcrypt 알고리즘 자체가 72바이트를 넘는 입력을 조용히 잘라버리는 제약이 있어서, 긴 비밀번호를 쓰는
사용자는 실제로는 앞 72바이트만으로 로그인되는 문제가 생깁니다. sha256로 먼저 고정 길이(32바이트)
다이제스트를 만들면 이 문제가 없어지고, bcrypt의 salt+cost factor 보호는 그대로 유지됩니다. 이건
표준적으로 알려진 우회법입니다(passlib 등 라이브러리도 비슷하게 처리).

### 2.4 배포 / 운영

**Q. 왜 Vercel을 선택했나요? AWS나 별도 서버는 고려 안 했나요?**
A. 무료로 시작할 수 있고(포트폴리오 프로젝트라 비용이 중요), Git 푸시만으로 프런트/백엔드가 함께
배포되는 워크플로우가 빠릅니다. 다만 서버리스라서 상시 프로세스가 필요한 것(예: 디스코드 Gateway 봇)은
못 올라가는 트레이드오프가 있고, 그것 때문에 HTTP Interactions 방식을 별도로 만들었습니다.

**Q. 서버리스에서 스케줄된 작업(매일 자정 리포트)은 어떻게 돌리나요?**
A. 로컬/상시 서버에서는 asyncio 백그라운드 루프가 다음 실행 시각까지 대기했다가 도는 방식이지만,
Vercel 함수는 요청이 끝나면 프로세스가 사라지기 때문에 이 루프가 살아있을 수 없습니다. 대신 Vercel Cron이
정해진 시각에 크론 전용 엔드포인트(`/internal/cron/*`)를 호출하고, 그 요청이 진짜 Vercel Cron에서 온 건지
`CRON_SECRET`으로 검증합니다.

**Q. (27번 슬라이드 관련) 그 URL 버그, 애초에 어떻게 발견했나요?**
A. 사용자가 "AI 리포트에서 데이터를 못 불러온다"고 알려줘서 시작했습니다. 먼저 로컬에서 실제 프로덕션
DB에 연결해서 똑같은 쿼리를 돌려봤는데 성공했어요 — 그래서 SQL이나 데이터 문제가 아니라는 걸 알았습니다.
그다음 실제 배포된 엔드포인트에 curl로 직접 요청을 보내봤더니 재현이 됐고, 실패 속도(0.3초 vs 정상 몇 초)를
보고 "이건 진짜 네트워크 호출이 아니라 즉시 실패하는 것"이라는 가설을 세워서 하나씩 좁혀갔습니다.

**Q. 이런 종류의 버그를 앞으로 어떻게 예방할 건가요?**
A. 로컬 재현이 안 되는 클래스의 버그였기 때문에, 배포 환경에서 실제로 자기 자신을 호출하는 로직은
헬스체크나 스모크 테스트로 배포 직후 검증하는 절차가 필요하다고 느꼈습니다. 지금은 수동으로 curl을
쳐서 확인했지만, 이상적으로는 배포 파이프라인에 "배포 후 핵심 엔드포인트 자동 점검" 단계를 추가하는 게
다음 개선 항목입니다.

### 2.5 Discord 봇

**Q. 왜 봇을 두 가지 방식으로 만들었나요? 하나만 있으면 안 되나요?**
A. 처음엔 discord.py Gateway 방식(`bot.py`)만 있었는데, 이건 상시 WebSocket 연결이 필요해서 Vercel
서버리스 함수로 못 올라갑니다. 나머지 시스템 전부를 Vercel 하나에 배포하는 게 목표였기 때문에,
Discord의 HTTP Interactions 방식으로 다시 만들어서 서버리스에 맞게 포팅했습니다. Gateway 방식 코드는
로컬/상시 서버에서 쓸 수 있게 남겨뒀습니다.

**Q. 봇이 디스코드에 "오프라인"으로 뜨는데 정상 작동하는 게 맞나요?**
A. 네, 이건 화면 표시 문제일 뿐입니다. "온라인" 상태는 Gateway가 유지하는 프레즌스(presence)인데,
HTTP Interactions 방식은 애초에 Gateway 연결 자체가 없어서 프레즌스를 보낼 수가 없습니다. 슬래시
명령은 Discord가 등록된 엔드포인트 URL로 직접 HTTP 요청을 보내는 거라 온라인 여부와 무관하게 동작합니다.

**Q. 웹훅 URL이 유출되면 위험하지 않나요?**
A. 웹훅 URL을 아는 사람은 누구나 그 채널에 메시지를 보낼 수 있어서 민감한 값입니다. DB에는 저장하지만
API 응답에는 판매자 본인 토큰으로 인증된 `/sellers/me/discord` 요청에서만 노출되고, 관리자 전용 채널
웹훅과 판매자 채널 웹훅은 물리적으로 분리돼 있어 한쪽이 새도 다른 쪽까지 영향이 없습니다. 실제 운영이라면
웹훅 URL 로테이션 기능도 필요하다고 생각합니다.

**Q. 서명 검증(`verify_signature`)을 왜 직접 구현했나요? 라이브러리는 없나요?**
A. PyNaCl의 `VerifyKey.verify()`가 이미 라이브러리 함수입니다 — Ed25519 서명 검증 자체는 PyNaCl이
하고, 저희 코드는 그걸 Discord가 요구하는 방식(타임스탬프+바디를 이어붙여서 검증)으로 감싸는
얇은 wrapper입니다. Discord 공식 문서가 이 패턴을 그대로 안내합니다.

### 2.6 한계 / 압박 질문

**Q. 이거 진짜 RAG 아니잖아요? "지식 검색"이라면서요.**
A. 맞습니다, 지금은 진짜 RAG가 아니라 Langfuse에서 프롬프트 버전을 "조회"하는 것뿐입니다. 정직하게
한계 슬라이드에 그렇게 적어뒀고, 다음 단계로 실제 지식문서를 임베딩해서 벡터 검색을 붙이는 걸
로드맵에 넣어뒀습니다.

**Q. 재시도 로직이 없다고 했는데, 그럼 OpenRouter가 잠깐 죽으면 어떻게 되나요?**
A. `allow_fallbacks`로 OpenRouter가 다른 모델 제공자로 자동 전환하는 것까지는 되지만, 애플리케이션
레벨에서 "실패하면 N번 재시도"하는 로직은 없습니다. 지금은 실패하면 사용자에게 에러가 그대로 갑니다.
Discord 알림은 예외적으로 `DiscordNotifier.send()`가 절대 예외를 던지지 않게 만들어서, 알림 실패가
전체 파이프라인을 죽이지는 않게 해뒀습니다.

**Q. 결제가 실제 PG 연동이 아니라 모사(mock)라고 했는데, 그럼 이 프로젝트가 증명하는 건 뭔가요?**
A. 이 프로젝트가 보여주려는 핵심은 결제 처리 자체가 아니라 "커머스 이벤트가 발생했을 때 그 데이터를
어떻게 신뢰할 수 있는 숫자로 만들고, AI가 그걸 어떻게 안전하게 해석해서 전달하는가"입니다. 실제 PG
연동은 인터페이스만 바뀌는 부분이라, 이벤트 원장과 AI 파이프라인 설계가 바뀔 필요는 없습니다.

**Q. 이 프로젝트에서 가장 자신 없는 부분은 어디인가요?**
A. (정직하게 답하는 게 중요한 질문입니다) SQL 정규식 변환 기반의 DB 이중 백엔드 지원이 가장 위험한
설계라고 생각합니다. 실제로 배포 후 두 번이나 버그가 났고, 테스트 스위트가 SQLite로만 돌아서 Postgres
전용 문제를 구조적으로 못 잡습니다. 프로덕션이라면 SQLAlchemy 같은 정식 ORM이나, 최소한 CI에서
Postgres 컨테이너로도 테스트를 돌리는 게 맞다고 생각합니다.
